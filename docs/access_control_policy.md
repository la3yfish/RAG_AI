# Access Control & Data Classification (RBAC + Levels)

> Цель: формализовать уровни доступа `public/internal/confidential` и минимальный RBAC, чтобы фильтровать retrieval и выдачу источников в RAG.
> Контекст: RAG Retrieval использует фильтры `department` и `access_level`. (см. `docs/system_prompt.md`, `docs/knowledge_base.md`)

## 1) Термины

- **access_level**: классификация документа: `public | internal | confidential`.
- **clearance**: максимальный `access_level`, который разрешён пользователю.
- **department**: принадлежность документа отделу (Sales, Engineering, ProcurementLogistics, QualityClaims, FinanceAdmin, HR).
- **scope**: область видимости по отделам: `own_dept | cross_dept | all_depts`.
- **actions**: что пользователь может делать в системе (query / sources / ingest / analytics / admin).

## 2) Уровни доступа: смысл и типовые примеры

### 2.1 public

**Определение:** информация, допустимая к распространению вне компании.

Типовые примеры (документ/фрагмент):

- общие описания компании, публичные презентации, обезличенные кейсы
- общие продуктовые/маркетинговые материалы

### 2.2 internal

**Определение:** внутренняя служебная информация, не предназначенная для внешней публикации.

Типовые примеры:

- внутренние регламенты и инструкции
- обезличенные операционные KPI/дашборды (без персональных данных и коммерческих условий)
- технические справочники/шаблоны без чувствительных цен/контрактов

### 2.3 confidential

**Определение:** чувствительная информация, доступная только ограниченному кругу лиц по необходимости.

Типовые примеры (для UnitTech как B2B компании):

- договоры с клиентами/поставщиками, коммерческие условия, цены, скидки
- финансовые документы (выручка, маржинальность, затраты, платежи), бухгалтерия
- персональные данные сотрудников, кадровые документы, оценка эффективности
- рекламации/качество с конкретными контрагентами, серийными номерами, поставками и т.п.

## 3) Минимальный RBAC

### 3.1 Роли

- **Guest**: внешний/публичный пользователь.
- **Employee**: сотрудник компании (базовый доступ).
- **DepartmentHead**: руководитель отдела.
- **HR**: сотрудник отдела кадров.
- **FinanceAdmin**: финансово-административный отдел (бухгалтерия/договорная).
- **Executive**: руководство (директор/топ-менеджмент).
- **SystemAdmin**: тех. админ (управление системой; контент-доступ отдельно ограничивается политикой).

### 3.2 Привязка ролей к clearance и scope (по умолчанию)

- **Guest** → `public`, scope=`all_depts` (только public)
- **Employee** → `internal`, scope=`own_dept`
- **DepartmentHead** → `confidential`, scope=`own_dept` (+ выборочно cross_dept по бизнес-необходимости)
- **HR** → `confidential`, scope=`HR` + `all_depts` для HR-документов (но не для коммерческих условий других отделов)
- **FinanceAdmin** → `confidential`, scope=`FinanceAdmin` + `cross_dept` для договоров/счетов (по необходимости)
- **Executive** → `confidential`, scope=`all_depts`
- **SystemAdmin** → `internal`, scope=`all_depts` для технических артефактов; `confidential` контент **не открывать по умолчанию** (только через отдельное «break-glass» правило и аудит)

## 4) Политика по отделам (department)

Оргструктура компании включает отделы: продажи, инженерно-технический, закупки/логистика, качество/рекламации, финансово-административный, HR.

### 4.1 Правило видимости по department

- Базово: `scope=own_dept` (сотрудник видит только документы своего отдела).
- Исключения:
  - `Executive`: `all_depts`
  - `FinanceAdmin`: `cross_dept` на документы, где Finance/договорная участвуют (счета, договоры, платежные документы)
  - `HR`: доступ к HR-документам по всем отделам (персонал), но без права смотреть коммерческие условия, не относящиеся к HR

### 4.2 Cross-department документы

Для документов, которые нужны нескольким отделам, вводится явный флаг:

- `share_scope = "cross_dept"` и список `shared_with_departments=[...]` (или `shared_with_roles=[...]`)

## 5) Матрица доступа (контент и функции)

### 5.1 Контент (чтение источников в RAG)

- **Ответ LLM**: можно показывать всем, но только на основе разрешённых пользователю источников.
- **Источники/цитаты**: показывать только если пользователь имеет доступ к соответствующему документу/чанку.
- **Полный текст документа**: отдельно, по тем же правилам что и retrieval.

### 5.2 Функции (endpoints/UI)

- `POST /query` — все роли (но сервер сам применяет фильтры).
- `POST /ingest` — только `DepartmentHead`, `SystemAdmin`, (опционально `FinanceAdmin`, `HR`) — в зависимости от политики.
- `/analytics` — `Employee+`, но с агрегациями/обезличиванием; финансовые/HR отчеты — только `FinanceAdmin/HR/Executive`.

## 6) Enforcement: как именно применять фильтры

### 6.1 Не доверять client-side access_level

Frontend может отправлять `access_level`, но backend обязан:

1) определить пользователя (auth)
2) вычислить **effective_clearance** = min(user.clearance, requested_access_level)
3) применить фильтры в retriever: `access_level <= effective_clearance` и `department` в рамках scope

### 6.2 Правило сравнения access_level

Упорядочивание: `public` < `internal` < `confidential`.

### 6.3 Vector store metadata

В каждый chunk метаданные:

- `access_level`
- `department`
- (опционально) `share_scope`, `shared_with_roles`, `shared_with_departments`

## 7) Правила классификации документов при ingestion (по умолчанию)

Если документ не размечен:

- **default**: `internal`
- **confidential** если найдено:
  - персональные данные / кадровые документы
  - финансы/оплаты/счета/зарплаты
  - цены/скидки/коммерческие условия/контракты/договоры
  - рекламации с привязкой к контрагентам/поставкам
- **public** — только если явно помечено (или источник в публичном разделе)

Рекомендация: поддержать ручной override в UI `/ingest` (выпадающие списки `access_level`, `department`, `share_scope`).

## 8) Аудит и логирование

В логах запросов уже предусмотрены `access_level_filter` и `top_sources`; дополнить:

- `user_id`, `role`, `department`, `effective_clearance`, `scope`
- отметка `policy_decision = allow|deny` для случаев отказа/пустой выдачи
